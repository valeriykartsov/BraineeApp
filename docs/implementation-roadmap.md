# Roadmap реализации BraineeApp

Статус: порядок согласован владельцем 2026-10-20 (D-01). Решения — в `docs/decisions.md`. Одна задача = одна ветка = один PR, если не сказано иное.
Перед каждой задачей: зелёные тесты на `main`. После: список изменений, проверок, рисков и ручной работы.

Команда тестов (подтверждена 2026-10-20):

```bash
xcodebuild test -project BraineeApp.xcodeproj -scheme BraineeApp -destination 'platform=iOS Simulator,name=iPhone 16,OS=18.3.1' -only-testing:BraineeAppTests
```

## Изменения относительно исходного порядка из брифа

| Изменение | Причина (ссылки на `architecture-audit.md`) |
|---|---|
| Добавлена фаза **1 «Страховка и домен»** перед SwiftData | Нет тестов persistence-слоя и нет пользовательского экспорта (R11); битый файл может быть перезаписан пустым (R2). Сначала страховочная сетка, потом миграция |
| Вынесение мутаций в `TaskService` **до** SwiftData | Мутации задач продублированы в 3 View (R7); миграцию, календарь и outbox удобнее подключать в одной точке |
| Поля `updatedAt`/`completedAt`/`UserProfile.uuid` — **до** включения постоянного хранилища | Чтобы первая постоянная схема SwiftData (V1) уже содержала поля для синхронизации и отчётов, без второй миграции схемы |
| «Создать модели SwiftData» заменено на «включить постоянное хранилище существующих моделей» | Модели уже есть, только in-memory (аудит §1) |
| JSON-импорт выделен в отдельную задачу после переключения | Импорт с заменой данных — отдельный риск, не смешиваем с миграцией |
| Серверный `ReportService` — до Telegram; клиентская синхронизация — односторонняя | Отчёты — единая бизнес-логика; один писатель снимает вопрос конфликтов (D-09) |
| Фазы Календарь / Markdown / LLM независимы друг от друга | Их порядок можно менять по вашему приоритету после фазы 2 |

## Фаза 1 — Страховка и доменный слой (без смены хранилища)

### BASE-1. Характеризационные тесты persistence-слоя
- **Цель:** зафиксировать текущее поведение `AppDataStore` и `AppDataPersistence` тестами до любых изменений.
- **Предусловия:** A-0.
- **Файлы:** `BraineeApp/Persistence/AppDataStore.swift` (минимальная точка внедрения каталога/Keychain-аккаунта для тестов), новые `BraineeAppTests/AppDataStoreTests.swift`, `BraineeAppTests/AppDataPersistenceRoundTripTests.swift`.
- **Изменения:** возможность указать временный каталог и префикс Keychain-аккаунта (по умолчанию — как сейчас); поведение приложения не меняется.
- **Готово, когда:** тесты покрывают round-trip JSON → SwiftData → JSON без потерь (все поля всех сущностей), выбор свежей копии файл/Keychain, восстановление файла из Keychain.
- **Автотесты:** перечисленные выше; все 142 существующих зелёные.
- **Ручные проверки:** запуск приложения, данные на месте.
- **Риски:** тесты Keychain на симуляторе могут вести себя иначе, чем на устройстве — изолировать аккаунт/сервис.
- **Зависимости:** —.

### BASE-2. Ручной экспорт бэкапа JSON
- **Цель:** дать возможность вынуть данные с устройства до миграции.
- **Предусловия:** BASE-1.
- **Файлы:** `Views/Profile/ProfileView.swift` (кнопка), новый `Persistence/BackupExport.swift` (`BackupDocument`, `BackupFile`).
- **Изменения:** `fileExporter` сохраняет один JSON-файл бэкапа (формат — D-16) в Files.
- **Готово, когда:** экспортированный файл открывается, вложенный `tasks` декодируется существующим `MyTasksDocument` и содержит все задачи.
- **Автотесты:** encode/decode бэкап-документа.
- **Ручные проверки:** экспорт на устройстве в Files/iCloud Drive, сравнение числа задач.
- **Риски:** аватар в base64 увеличивает файл — допустимо.
- **Зависимости:** BASE-1.

### BASE-3. Защита от перезаписи битого файла
- **Цель:** устранить R2: нечитаемый `mytasks.json` не должен молча заменяться пустыми данными.
- **Файлы:** `Persistence/AppDataStore.swift`, `Views/AppRootView.swift`.
- **Изменения:** если файл существует, но не декодируется, — переименовать в `mytasks.corrupt-<timestamp>.json`, попробовать Keychain-копию, при неудаче показать ошибку и **не** записывать пустой документ.
- **Выполнено (2026-10-20), сверх плана:** то же правило для `profile.json` (раньше битый профиль давал ошибку при каждом запуске); ошибка чтения с диска больше не считается «файла нет» — пробрасывается без переименования; исправлен `AppRootView` — заставка перекрывала экран ошибки навсегда.
- **Готово, когда:** тест «битый файл + пустой Keychain → ошибка, файл сохранён» проходит.
- **Автотесты:** сценарии битого файла (BASE-1 инфраструктура).
- **Ручные проверки:** подложить битый файл в симуляторе.
- **Риски:** изменение пути старта — проверить первый запуск без файлов.
- **Зависимости:** BASE-1.

### DOM-1. `TaskService`: единая точка мутаций задач
- **Цель:** убрать дубли `addTask`/`updateTask`/`toggleTask`/`setStatus`/`softDelete` из `TaskSectionView`, `CalendarWeekView`, `EisenhowerQuadrantDetailView`.
- **Файлы:** новый `BraineeApp/Domain/TaskService.swift`; три перечисленных View.
- **Изменения:** перенос логики без изменения поведения; сервис вызывает `persistToJSON()` как сейчас.
- **Готово, когда:** во View нет прямых изменений полей `TaskItem` для этих операций; поведение идентично.
- **Автотесты:** `TaskServiceTests` (создание, обновление, переключение с перестановкой `sortOrder`, мягкое удаление).
- **Ручные проверки:** сценарии задач из `TEST_SCENARIOS.md` на всех трёх экранах.
- **Риски:** анимации `withAnimation` остаются во View — сервис не должен зависеть от SwiftUI.
- **Выполнено (2026-10-20):** `Domain/TaskService.swift` (`create`, `update`, `toggleCompletion`, `setStatus`, `softDelete`, внедряемый `onChange`). Единственное изменение поведения: отметка выполнения в Матрице теперь тоже переносит задачу в конец её группы, как в «Задачах» и «Календаре».
- **Зависимости:** BASE-1.

### DOM-2. Сервисы для групп, тегов, привычек, корзины
- **Цель:** провести остальные мутации (`TaskOrganizedListView`, `TagLibraryView`, `HabitsView`, `DeletedTasksFolderView`, `ProfileView`) через сервисы.
- **Файлы:** `Domain/GroupService.swift`, `TagService.swift`, `HabitService.swift`, `ProfileService.swift` + View.
- **Готово, когда:** `persistToJSON()` вызывается только из сервисов и `JSONPersistenceModifier`.
- **Автотесты:** по сервису на основные операции.
- **Ручные проверки:** группы (drag-and-drop), теги, привычки, корзина.
- **Риски:** большой diff — допускается разбить на 2 PR (задачи/группы и привычки/теги/профиль).
- **Зависимости:** DOM-1.
- **Разбивка (2026-10-20):**
  - **DOM-2a — выполнено:** `GroupService` (создание, переименование, удаление), `TagService` (создание, переименование, удаление), `TaskService.move/restore/permanentlyDelete`; экраны `TaskSectionView`, `TaskOrganizedListView`, `TagLibraryView`, `DeletedTasksFolderView`. Добавлена защита: `permanentlyDelete` стирает только задачи из корзины.
  - **DOM-2b — выполнено:** `HabitService` (`HabitsView`: создание, переименование, отметка дня с правилом `HabitDaySelection.clamp`, удаление, перестановка с одним сохранением в конце), `ProfileService` (`ProfileView`, `AppearanceSettingsView`).

### DOM-3. Поля для синхронизации и отчётов (JSON v9)
- **Цель:** добавить `updatedAt` (задачи, группы, теги, привычки), `completedAt` (задачи), `uuid` профиля.
- **Файлы:** `Models/*.swift`, `Persistence/AppDataDocuments.swift`, `AppDataPersistence.swift`, сервисы.
- **Изменения:** `decodeIfPresent` со значениями по умолчанию (`updatedAt = createdAt`, `completedAt = nil`/по статусу → D-03), `MyTasksDocument.currentVersion = 9`; сервисы проставляют `updatedAt`.
- **Готово, когда:** файл v8 читается без потерь, v9 пишется; любое изменение через сервис меняет `updatedAt`.
- **Автотесты:** обратная совместимость v8 → v9, `updatedAt` после операций.
- **Ручные проверки:** обновление приложения поверх существующих данных.
- **Риски:** старая версия приложения не прочитает новые поля — не страшно (лишние ключи игнорируются).
- **Зависимости:** DOM-2.
- **Выполнено (2026-10-20):** `updatedAt` у задач, групп, тегов, привычек (сервисы проставляют; при удалении группы/тега обновляются затронутые задачи; при перестановке привычек — только сдвинутые); `completedAt` ставится/сбрасывается в сеттере `TaskItem.status`; `UserProfile.uuid` ↔ `ProfileDocument.id` (старый профиль получает id при первом запуске и сразу сохраняется). Форматы: `mytasks.json` v9, `profile.json` v4. Сервисы получили внедряемое `now` для тестов.

## Фаза 2 — SwiftData как основное хранилище

### SD-1. Версионированная схема и постоянный контейнер (не включён)
- **Цель:** подготовить `SchemaV1` (`VersionedSchema`) и `MigrationPlan`, фабрику контейнера с выбором in-memory / persistent.
- **Файлы:** `Persistence/Schema/SchemaV1.swift`, `Persistence/ModelContainerFactory.swift`, `BraineeAppApp.swift` (по-прежнему in-memory).
- **Готово, когда:** тест создаёт persistent-контейнер во временном каталоге, пишет и перечитывает все сущности.
- **Автотесты:** round-trip через файл хранилища.
- **Ручные проверки:** приложение работает как раньше.
- **Риски:** `@Model` внутри `VersionedSchema` требует аккуратного именования типов (typealias на текущую версию).
- **Зависимости:** DOM-3.

### SD-2. Мигратор JSON → SwiftData (не подключён к старту)
- **Цель:** реализовать и протестировать перенос в изоляции.
- **Файлы:** `Persistence/JSONToSwiftDataMigrator.swift`, `BraineeAppTests/JSONToSwiftDataMigratorTests.swift`.
- **Изменения:** копия исходных файлов в `Application Support/Backups/pre-swiftdata-<дата>/`; upsert по `uuid`; проверка по каждому `uuid`; маркер завершения ставится только после проверки; отчёт (сколько перенесено/отброшено нормализацией).
- **Готово, когда:** повторный запуск не создаёт дублей; при ошибке маркер не ставится; отчёт совпадает с ожиданием.
- **Автотесты:** пустые данные, обычный набор, дубликаты UUID, висячие ссылки, >7 привычек, повторный запуск, сбой в середине.
- **Ручные проверки:** нет (не подключён).
- **Риски:** R3 (нормализация отбрасывает данные) — отражать в отчёте.
- **Зависимости:** SD-1.

### SD-3. Переключение старта на постоянное хранилище (JSON пишется параллельно)
- **Цель:** приложение работает от SwiftData; JSON продолжает записываться как раньше — путь отката.
- **Файлы:** `BraineeAppApp.swift`, `AppDataPersistence.swift` (`bootstrap` без `clearAllData` для persistent-пути), `AppRootView.swift`.
- **Готово, когда:** после перезапуска данные читаются из хранилища; JSON и Keychain не изменились при первом запуске (кроме обычной записи после изменений); экран ошибки при сбое миграции.
- **Автотесты:** `bootstrap` с маркером/без маркера; отсутствие удаления данных при повторном старте.
- **Ручные проверки:** **обязательно** — BASE-2 экспорт на устройстве → установка сборки → сравнение количества задач/привычек/тегов/групп, проверка дат и статусов; виджет, уведомления, бейдж.
- **Риски:** R1 — главный риск всего плана. Ревью diff построчно.
- **Зависимости:** SD-2, BASE-2.

### SD-4. JSON — только бэкап
- **Цель:** перестать переписывать JSON и Keychain на каждое изменение.
- **Предусловия:** SD-3 стабильно отработал на устройстве (срок → D-04).
- **Файлы:** `AppDataPersistence.swift` (`persistToJSON` → `AppSideEffects.didChange`), `JSONPersistenceModifier`.
- **Изменения:** после изменения — `save()` + виджет + уведомления; JSON-автобэкап при уходе в фон с ограничением частоты; запись в Keychain прекращается (старые записи не удаляются).
- **Готово, когда:** изменение не трогает `mytasks.json`; автобэкап появляется по правилу.
- **Автотесты:** правило частоты бэкапа.
- **Ручные проверки:** изменения сохраняются после «убийства» приложения.
- **Зависимости:** SD-3.

### SD-5. Импорт (восстановление) из JSON-бэкапа
- **Цель:** восстановить данные из файла.
- **Файлы:** `Persistence/BackupImport.swift`, экран в профиле.
- **Изменения:** `fileImporter` → предпросмотр (количества) → подтверждение → перед заменой автоматически экспорт текущего состояния → замена. Аватара в бэкапе нет (D-16) — текущий аватар сохраняется. Режим слияния — отдельное решение.
- **Готово, когда:** восстановление из бэкапа BASE-2 даёт идентичные данные.
- **Автотесты:** импорт v8/v9, невалидный файл не меняет данные.
- **Ручные проверки:** полный цикл экспорт → удалить задачу → импорт.
- **Зависимости:** SD-4.

### SD-6. Удаление устаревшего пути хранения
- **Цель:** удалить Keychain-копии данных и код in-memory пути.
- **Предусловия:** **явное подтверждение владельца**; есть свежий бэкап.
- **Готово, когда:** Keychain содержит только секреты; `README.md`, `CLAUDE.md` обновлены.
- **Риски:** необратимо — выполнять последним в фазе.
- **Зависимости:** SD-5.

## Фаза 3 — Календарь iPhone (EventKit, односторонний экспорт в календарь «BraineeApp», iCloud; без Google — D-05)

### CAL-1. Проверка на устройстве (spike)
- **Цель:** подтвердить на вашем iPhone: запрос полного доступа к Календарю; приложение может создать календарь «BraineeApp» в iCloud (и что происходит, если iCloud-календари выключены); `eventIdentifier` не меняется после перезапуска и синхронизации iCloud; что видит приложение, если календарь «BraineeApp» удалён в Календаре.
- **Файлы:** временная ветка, код не сливается; результат — запись в `docs/decisions.md` (D-05/D-06).
- **Готово, когда:** ответы на вопросы записаны.
- **Зависимости:** DOM-1.
- **Статус:** выполнено 2026-10-20, результаты — D-05.

### CAL-2. Экспорт задач в календарь (правила D-06: 30 мин, выполненные удаляются)
- **Файлы:** `Integrations/Calendar/CalendarExportService.swift`, файл связей `calendar-links.json` (D-22), настройка «Экспорт в Календарь» (вкл/выкл, без выбора календаря), `Info.plist` (`NSCalendarsFullAccessUsageDescription`).
- **Изменения:** при включении — запрос доступа и создание календаря «BraineeApp» (iCloud, иначе локальный); создание/обновление/удаление события по правилам `target-architecture.md` §4.2, вызов из `AppSideEffects.didChange` (его вызывают все сервисы `Domain/`, в т.ч. `TaskService`, и восстановление из бэкапа) и при возврате в приложение; удалённый пользователем календарь создаётся заново.
- **Учесть по итогам CAL-1 (D-05):** календарь сначала ищется по сохранённому id, создание защищено от повторного вызова (иначе дубли); наличие календаря проверяется при каждом экспорте; на `EKEventStoreChanged` повторный экспорт не запускается; запасной поиск события по метке в `url`/`notes`.
- **Готово, когда:** изменение задачи обновляет то же событие; задача без даты не экспортируется; удаление/выполнение убирает событие; события только в календаре «BraineeApp».
- **Автотесты:** маппинг задача → параметры события (чистая функция); логика «создать/обновить/удалить» на фейковом хранилище событий.
- **Ручные проверки:** событие видно в календаре «BraineeApp» в Календаре iPhone (и на Mac/iPad через iCloud); отказ в доступе; календарь «BraineeApp» удалён вручную → создаётся заново.
- **Зависимости:** CAL-1, SD-3.
- **Статус:** выполнено 2026-10-21 (ветка `feature/cal-2-calendar-export`), проверено на iPhone.

### CAL-3. Пересинхронизация
- **Цель:** кнопка «пересоздать события» и сверка связей (`calendar-links.json`, D-22) с реальными событиями в календаре «BraineeApp».
- **Зависимости:** CAL-2.
- **Статус:** закрыт без реализации 2026-10-21 — сверка уже выполняется в CAL-2 (D-23).
