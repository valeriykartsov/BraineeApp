# Целевая архитектура BraineeApp

Статус: согласовано владельцем 2026-10-20, кроме D-11 (ждёт подтверждения). Основан на `docs/architecture-audit.md`.
Платформа: только iOS (D-13). «Цели» и «фокус» — тексты в Obsidian, отдельных сущностей нет (D-15).
Решения, требующие подтверждения, помечены **(→ D-xx)** и описаны в `docs/decisions.md`.

---

## 1. Принципы

1. **Offline-first.** Всё, что пользователь делает в приложении, работает без сети. Сервер, LLM, Telegram — необязательные надстройки.
2. **Одно место для каждого бизнес-правила.** Правила задач — в доменном сервисе приложения; правила отчётов — в серверном сервисе отчётов.
3. **Стабильные UUID** (`uuid` в моделях) — единственный внешний идентификатор. `PersistentIdentifier` SwiftData наружу не выходит.
4. **Сохранность данных важнее скорости.** Любой перенос данных: бэкап → копирование → проверка → переключение → (позже, с подтверждения) удаление старого.
5. **Минимум инфраструктуры.** Без сторонних Swift-пакетов, пока не доказано обратное; сервер — один процесс Python.

## 3. Локальный контур (iOS)

### 3.1 Слои и границы модулей

Отдельные Swift-пакеты/фреймворки не вводим: границы — это папки и типы внутри таргета `BraineeApp`.

| Слой | Папка | Ответственность | Не должен |
|---|---|---|---|
| UI | `Views/` | Отображение, `@Query` для чтения, вызов сервисов | Менять модели напрямую и вызывать побочные эффекты |
| Домен | `Domain/` (новая) | `TaskService`, `HabitService`, `TagService`, `GroupService`: создание/изменение/удаление, правила статусов, сортировка, tombstone | Знать о SwiftUI |
| Хранилище | `Persistence/` | `ModelContainer`, схема и её версии, миграция JSON → SwiftData, JSON-бэкап | Содержать бизнес-правила |
| Побочные эффекты | `Utilities/` → позже `Integrations/` | Уведомления, виджет, бейдж, EventKit, outbox | Быть вызванными из View напрямую |
| Внешние интеграции | `Integrations/LLM`, `Integrations/Calendar`, `Integrations/Sync` | HTTP-клиенты, EventKit, Keychain-секреты | Получать `ModelContext` (LLM) |

Переход к этой структуре — постепенный (см. roadmap): сначала один `TaskService`, заменяющий дублированные методы в `TaskSectionView`, `CalendarWeekView`, `EisenhowerQuadrantDetailView`.

### 3.2 Хранение

- **SwiftData persistent store** — источник правды. Схема описывается через `VersionedSchema` + `SchemaMigrationPlan` с первого постоянного релиза, чтобы будущие поля добавлялись управляемо.
- **Новые поля до включения постоянного хранилища (→ D-03):** `updatedAt: Date` у `TaskItem`, `TaskGroup`, `TaskTag`, `Habit`; `uuid` у `UserProfile`; `completedAt: Date?` у `TaskItem` (для отчётов `/closed`). Добавляются сначала в JSON v9 (с обратной совместимостью), затем входят в SwiftData Schema V1.
- **Tombstones (→ D-07):** при окончательном удалении сохраняется запись `DeletionRecord(entity, uuid, deletedAt)`. Нужна только для синхронизации, вводится вместе с синхронизацией, а не раньше.
- **JSON** — формат бэкапа и обмена: экспорт через `fileExporter`, импорт через `fileImporter` с предпросмотром и подтверждением. Используется тот же `MyTasksDocument`, чтобы старые файлы оставались читаемыми.
- **Keychain** — только секреты (→ D-02). Существующие Keychain-копии JSON остаются нетронутыми до подтверждённой успешной миграции, затем удаляются отдельной задачей с вашего подтверждения.
- **UserDefaults** — только настройки UI (тема, акцент, вкладки, уведомления). Дублирование темы/акцента в `profile.json` сохраняется только в бэкап-формате.

### 3.3 Миграция JSON → SwiftData (схема)

```
старт приложения
  ├─ маркер migration.v1.completed есть? ── да ─► обычная работа с persistent store
  └─ нет
       ├─ 1. Загрузить JSON (AppDataStore.loadTasks/loadProfile) — существующий код
       ├─ 2. Сохранить копию исходных файлов в Application Support/Backups/pre-swiftdata-<дата>/
       ├─ 3. Вставить записи в persistent store, upsert по uuid (повторный запуск не создаёт дублей)
       ├─ 4. Проверка: количество и поля по каждому uuid совпадают с нормализованным JSON
       ├─ 5a. ok → записать маркер; JSON и Keychain не трогать
       └─ 5b. ошибка → не ставить маркер, показать экран ошибки, работать по-старому (JSON → in-memory)
```

Идемпотентность обеспечивается upsert по `uuid` и маркером, который ставится **после** проверки.

### 3.4 Побочные эффекты после изменения

Вместо `persistToJSON()` (полная перезапись всего) — один метод, например `AppSideEffects.didChange(…)`, вызываемый доменным сервисом:

1. `modelContext.save()`;
2. снимок виджета;
3. пересчёт уведомлений и бейджа (как сейчас);
4. (позже) обновление календарного события изменённой задачи;
5. (позже) запись в outbox синхронизации.

Регулярный JSON-автобэкап — при уходе в фон, не чаще раза в N часов (→ D-04).

## 4. Календарь (EventKit)

### 4.1 Сравнение вариантов

| Критерий | EventKit **Calendar events** (`EKEvent`) | EventKit **Reminders** (`EKReminder`) | Google Calendar / Tasks API |
|---|---|---|---|
| Инфраструктура | Нет | Нет | OAuth-клиент Google, токены, сеть |
| Offline | Да (система синхронизирует сама) | Да | Нет |
| Видно в Google Calendar | Да, если целевой календарь принадлежит Google-аккаунту в iOS | **Нет** — Reminders синхронизируются через iCloud/Exchange, не Google | Да |
| Дата без времени | `isAllDay = true` | `dueDateComponents` без часа — естественно | Tasks API: только дата; Calendar API: all-day event |
| Дата + время | Слот с `startDate`/`endDate` (нужна длительность → D-06) | Срок с временем, но без «слота» | Слот |
| Статус «выполнено» | Нет понятия, только текст/удаление | Есть `isCompleted` | Tasks: есть |
| Обновление без дублей | Хранить `eventIdentifier` по `uuid` задачи | Хранить `calendarItemIdentifier` | Хранить id ресурса |
| Права | iOS 17+: `requestFullAccessToEvents` (write-only не позволяет найти событие для обновления) | `requestFullAccessToReminders` | OAuth consent |

### 4.2 Рекомендация для MVP

**EventKit Calendar events, односторонний экспорт BraineeApp → календарь** (→ D-05).
Причина: единственный вариант без инфраструктуры, который одновременно работает офлайн и попадает в Google Calendar через системную учётную запись iOS.

Правила:
- задача без `deadline` — не экспортируется; если дата была удалена — связанное событие удаляется;
- `hasDeadlineTime == false` → событие на весь день;
- `hasDeadlineTime == true` → событие `deadline … deadline + 30 мин` (D-06);
- задача выполнена или мягко удалена → событие удаляется (D-06); снятие отметки «выполнено» / восстановление → событие создаётся снова;
- соответствие `task.uuid → eventIdentifier` хранится локально (отдельная модель `CalendarLink`); если событие не найдено по идентификатору (его удалили в Календаре или идентификатор сменился после синхронизации) — создаётся заново, а не дублируется;
- пишем в один выбранный пользователем календарь; приложение не читает и не импортирует чужие события.

Ограничения: событие без понятия «выполнено»; `eventIdentifier` может меняться при пересинхронизации аккаунта (поэтому fallback-поиск по URL/метке в `notes`, → проверить в задаче CAL-2); создание отдельного календаря внутри Google-аккаунта из iOS может быть недоступно — тогда пользователь выбирает существующий календарь **[?] проверить на устройстве**.

## 5. LLM (OpenRouter напрямую из приложения)

```
View (черновик + подтверждение)
   ▲ TaskDraft (валидированный)
   │
LLMTaskDraftService ── собирает минимальный контекст (текст пользователя, дата/часовой пояс, список названий групп/тегов)
   │
LLMProvider (protocol) ── OpenRouterProvider (URLSession, JSON)
   │
LLMSettingsStore ── провайдер, модель (UserDefaults); API-ключ (Keychain)
```

- `protocol LLMProvider { func complete(_ request: LLMRequest) async throws -> LLMResponse }` — замена провайдера без изменения UI.
- Структурированный ответ: просим JSON по схеме; **всегда** декодируем в `TaskDraft` и валидируем (`TaskInputValidation`, допустимые enum'ы, дата не в прошлом при необходимости). Не полагаемся на то, что модель поддерживает `response_format` — проверяется в задаче LLM-3.
- Ошибки: нет сети, 401 (ключ), 402/429 (лимиты бесплатной модели), 5xx, тайм-аут (по умолчанию 30 с), невалидный JSON, превышение размера входа — каждое даёт понятное сообщение; ручное создание задачи всегда доступно.
- Данные наружу: только то, что нужно сценарию. Для «создать задачу» — только введённый текст + текущая дата + названия групп/тегов. Описания задач, профиль, аватар не отправляются.
- Агрегаты для рефлексии/отчётов считает код (`TaskStats`, `HabitProgress`); модель получает готовые числа и только формулирует текст.
- Ключ не логируется; `print` ошибок без тела запроса.

## 6. Просмотр Markdown (Obsidian)

- Выбор файла или папки vault через `fileImporter` (`.folder` / `UTType(filenameExtension: "md")`).
- Доступ сохраняется через **security-scoped bookmark** (`URL.bookmarkData()`), хранится в UserDefaults/SwiftData; при открытии — `startAccessingSecurityScopedResource()`/`stop…`; устаревший bookmark (`bookmarkDataIsStale`) пересоздаётся; недоступный файл → понятное сообщение и предложение выбрать заново.
- Для изображений по относительным путям нужен доступ к **папке** vault, не только к файлу.
- Рендер (→ D-08): собственный лёгкий разбор блоков (заголовки, списки, цитаты, код, горизонтальная линия) + `AttributedString(markdown:)` для инлайн-разметки внутри блока, в `LazyVStack` для длинных заметок. `WKWebView` — только если понадобятся таблицы/HTML.
- Obsidian-специфика (`[[wikilinks]]`, embed `![[img.png]]`) в MVP показывается как текст/простая ссылка на файл в той же папке.
- Только чтение. Никаких записей в файлы vault.
- Цели и фокус хранятся в заметках Obsidian (D-15), поэтому этот просмотрщик — единственный способ видеть их в приложении.

## 7. Сервер (Python-монолит)

- FastAPI + Pydantic + SQLite (`sqlite3` или SQLAlchemy Core — → D-10), pytest, миграции — пронумерованные SQL-файлы с таблицей `schema_version` (без Alembic, пока хватает).
- Структура: `server/app/{api,services,db,telegram}`, `server/migrations/NNN_*.sql`, `server/tests/`.
- Авторизация: один статический bearer-токен устройства (хранится на iPhone в Keychain, на сервере — в `.env`, не в git).
- Где работает: MacBook, запуск вручную, позже — `launchd` (задача OPS-1).

### 7.1 Синхронизация — что и как (→ D-09)

Исходная рекомендация: **односторонняя репликация iPhone → сервер**. Единственный писатель — приложение; сервер — read-only реплика для Telegram-отчётов. Это убирает разрешение конфликтов до появления второго пишущего клиента.

Синхронизируемые сущности (MVP): `TaskItem`, `TaskGroup`, `TaskTag`, `Habit` (D-09). Профиль, аватар и настройки UI не синхронизируются.

Протокол:
- клиент хранит **outbox** (`PendingChange(id: UUID, entity, entityUUID, op: upsert|delete, payload, updatedAt, attempts)`); запись в outbox — в той же транзакции SwiftData, что и изменение;
- `POST /api/v1/changes` пакетом; каждое изменение имеет `change_id` (UUID) — сервер хранит обработанные id → повтор запроса безопасен (идемпотентность);
- сервер применяет «последняя запись по `updated_at` побеждает» (при одном писателе конфликтов фактически нет);
- удаление = tombstone с `deleted_at`;
- ретраи с экспоненциальной задержкой; нет связи → outbox просто ждёт;
- первичная выгрузка — полный снимок через тот же endpoint.

Двусторонняя синхронизация — отдельное решение после появления сценария, где сервер или другой клиент меняют данные.

### 7.2 Доступ iPhone → MacBook (D-11, ждёт подтверждения)

- uvicorn слушает только `127.0.0.1:8000`; `tailscale serve` публикует его в личной сети Tailscale по HTTPS на имени `https://<mac>.<tailnet>.ts.net`.
- В приложении задаются базовый URL и токен; исключения ATS и разрешение локальной сети не нужны.
- В симуляторе используется `http://127.0.0.1:8000`.
- Сервер спит или VPN выключен → клиент воспринимает это как «нет сети».

## 8. Telegram-бот

- Тот же процесс, что и FastAPI (фоновая задача long polling) или отдельная команда `python -m app.telegram` с той же БД (→ D-12).
- Команды `/today`, `/week`, `/all`, `/closed`, `/help` вызывают **только** `ReportService` (`server/app/services/reports.py`); обработчики Telegram лишь форматируют и отправляют.
- Allowlist по `user_id` из `.env`; чужие сообщения игнорируются (без ответа).
- Бот читает данные только из серверной SQLite (D-09); к iPhone не обращается.
- Периоды: часовой пояс отчётов задаётся в конфиге и совпадает с часовым поясом iPhone (R9/R10 аудита); `/week` — текущая ISO-неделя пн–вс; `/closed` — последние N закрытых или `/closed 7d`.
- Статистика привычек за интервал отчёта — **только в `/today` и `/week`** (выполнено/всего по дням); в `/all` и `/closed` её нет.
- Ограничение размера: сообщение ≤ 4096 символов (лимит Telegram), лишнее обрезается с подсказкой «ещё N».
- Отчёт показывает время последней синхронизации, чтобы было видно, насколько данные свежие.

## 9. Обработка ошибок (сводно)

| Ситуация | Поведение |
|---|---|
| Ошибка чтения хранилища при старте | Экран ошибки с вариантами «повторить» / «восстановить из бэкапа»; никогда не перезаписывать данные пустым состоянием |
| Миграция не прошла проверку | Маркер не ставится, остаётся старый путь, лог причины |
| Нет прав на календарь | Экспорт выключен, в настройках объяснение и кнопка в «Настройки» |
| LLM недоступна / лимит | Сообщение + ручная форма; данные не меняются |
| Сервер недоступен | Outbox копится, индикатор «не синхронизировано с …» |
| Markdown-файл недоступен | Сообщение и «выбрать заново» |
| Telegram: чужой пользователь | Игнор |
