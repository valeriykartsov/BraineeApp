# Архитектурные решения BraineeApp

Формат: контекст → варианты → рекомендация → статус.
Статусы: **Предложено** (ждёт подтверждения владельца), **Принято**, **Отклонено**, **Заменено**.

---

## D-01. Порядок модернизации: страховка и домен до смены хранилища
- **Контекст:** persistence-слой без тестов, бэкапа для пользователя нет, мутации продублированы (аудит R2, R7, R11).
- **Варианты:** (а) сразу SwiftData persistent; (б) сначала тесты, экспорт, `TaskService`, новые поля.
- **Рекомендация:** (б). Дольше на 4–6 небольших PR, но миграция пройдёт по проверенному пути с возможностью отката.
- **Статус:** Принято (2026-10-20).

## D-02. Роль Keychain
- **Контекст:** сейчас Keychain хранит полные JSON-документы (включая аватар) как бэкап, переживающий переустановку (`KeychainStorage`, `AppDataStore`). Бриф: Keychain — только секреты.
- **Варианты:** (а) сохранить Keychain-зеркало данных навсегда; (б) после стабильной миграции прекратить запись (SD-4), позже удалить записи (SD-6) с подтверждения; бэкап — файлы JSON.
- **Рекомендация:** (б). Обратите внимание: вы потеряете автоматическое восстановление данных после **удаления и переустановки** приложения. Замена — ручной/авто-бэкап в Files (iCloud Drive).
- **Решение владельца:** автоматическое восстановление после переустановки не требуется; бэкап — JSON-файлы в Files.
- **Статус:** Принято (2026-10-20).

## D-03. Новые поля модели до постоянной схемы
- **Контекст:** нет `updatedAt`, `completedAt`, `UserProfile.uuid` (аудит R4, R5).
- **Рекомендация:** добавить в JSON v9 и модели до SD-1. Значения для старых записей: `updatedAt = createdAt`; `completedAt = nil` (для уже выполненных задач дата закрытия неизвестна — в отчётах `/closed` они не появятся или появятся с пометкой).
- **Решение владельца:** для старых выполненных задач `completedAt = nil` (дата закрытия неизвестна).
- **Статус:** Принято (2026-10-20).

## D-04. Когда JSON перестаёт быть основным
- **Рекомендация:** после SD-3 минимум 7 дней ежедневного использования без проблем, затем SD-4. Автобэкап JSON — при уходе в фон, не чаще раза в 24 часа, хранить последние 7 файлов в `Application Support/Backups/`.
- **Статус:** Предложено.

## D-05. Тип объекта для календаря
- **Контекст:** сравнение в `target-architecture.md` §4.1.
- **Варианты:** EventKit events; EventKit reminders; Google Calendar/Tasks API.
- **Рекомендация:** EventKit **events**, односторонний экспорт. Reminders не попадают в Google; Google API требует OAuth и сеть.
- **Проверить на устройстве (CAL-1):** запись в календарь Google-аккаунта, стабильность `eventIdentifier`, возможность создать отдельный календарь.
- **Статус:** Принято (2026-10-20); технические детали уточняются в CAL-1.

## D-06. Правила событий календаря
- **Решение владельца:**
  1. Задача со временем → событие длительностью 30 минут.
  2. Выполненная задача → событие удаляется.
  3. Мягко удалённая задача → событие удаляется.
  4. Задача без даты → не экспортируется; дата без времени → событие на весь день.
- **Статус:** Принято (2026-10-20).

## D-07. Tombstones
- **Рекомендация:** вводить вместе с синхронизацией (SYNC-1), не раньше. До этого окончательное удаление остаётся бесследным, как сейчас.
- **Статус:** Предложено.

## D-08. Рендер Markdown
- **Варианты:** (а) собственный блочный парсер + `AttributedString(markdown:)`; (б) SPM-пакет (например, Apple `swift-markdown` для разбора); (в) `WKWebView` + JS-библиотека.
- **Рекомендация:** (а) — без зависимостей, достаточно для заметок; (б) — если (а) окажется недостаточным для таблиц/вложенных списков; (в) — только при реальной необходимости.
- **Статус:** Предложено.

## D-09. Направление и объём синхронизации
- **Варианты:** (а) односторонняя iPhone → сервер, сервер — read-only реплика для отчётов; (б) двусторонняя.
- **Рекомендация:** (а). Telegram-бот только читает, других пишущих клиентов нет — конфликтов не возникает. Двусторонняя — отдельное решение при появлении сценария.
- **Решение владельца:** односторонняя синхронизация; Telegram-бот читает данные только с сервера. Привычки синхронизируются: статистика привычек за интервал отчёта выводится **только в `/today` и `/week`**; в `/all`, `/closed`, `/help` — не выводится.
- **Следствие:** на сервер передаются `Habit` (uuid, название, порядок, дни выполнения `yyyy-MM-dd`). Дни привычек — строки в часовом поясе устройства (аудит R9), поэтому отчёты сервера считаются в одном настроенном часовом поясе, совпадающем с часовым поясом iPhone.
- **Статус:** Принято (2026-10-20).

## D-10. Доступ к SQLite на сервере
- **Варианты:** `sqlite3` из стандартной библиотеки + SQL-миграции; SQLAlchemy Core; SQLModel/ORM + Alembic.
- **Рекомендация:** `sqlite3` + пронумерованные SQL-файлы и таблица `schema_version`. Меньше зависимостей и «магии»; легко читать.
- **Статус:** Предложено.

## D-11. Сетевой путь iPhone → MacBook
- **Контекст:** сервер работает на MacBook, который может спать или быть в другой сети. Telegram-боту входящий доступ не нужен: long polling — это исходящие запросы с MacBook к Telegram.
- **Варианты:**

  | Вариант | Плюсы | Минусы |
  |---|---|---|
  | (а) Локальная Wi-Fi сеть, HTTP по IP/`.local` | Ничего не устанавливать | Только дома; нужны исключение ATS и разрешение «Локальная сеть» на iPhone; IP Mac меняется; трафик не шифруется |
  | (б) **Tailscale + `tailscale serve`** | Работает дома и вне дома; HTTPS с настоящим сертификатом на постоянном имени `<mac>.<tailnet>.ts.net` → **никаких исключений ATS** в приложении; порты наружу не открываются; бесплатно для личного использования | Нужны аккаунт Tailscale и приложение Tailscale на Mac и iPhone; VPN на iPhone должен быть включён (можно настроить «по требованию») |
  | (в) Публичный туннель (Cloudflare Tunnel, ngrok) | Доступ откуда угодно без VPN | Сервер с личными данными открыт в интернет, вся защита держится на одном токене — не рекомендуется |

- **Рекомендация:** (б).
  - Сервер (uvicorn) слушает только `127.0.0.1:8000`. Команда `tailscale serve` публикует его в tailnet по HTTPS (в админке Tailscale нужно один раз включить MagicDNS и HTTPS-сертификаты).
  - В настройках приложения: базовый URL `https://<mac>.<tailnet>.ts.net` и bearer-токен (Keychain).
  - Тот же код клиента без изменений работает с `http://127.0.0.1:8000` в симуляторе: на этот адрес ATS исключений не требует.
  - Сервер недоступен (Mac спит, VPN выключен) → для приложения это обычное «нет сети», изменения ждут в outbox.
- **Почему не (а) для начала:** (а) не проще. Пришлось бы добавить исключения ATS и разрешение локальной сети, а при переходе на (б) убрать их. С (б) клиент с самого начала работает по HTTPS.
- **Ручная работа владельца (в задаче SYNC-2):** установить Tailscale на Mac и iPhone, войти в один аккаунт, включить HTTPS-сертификаты, выполнить `tailscale serve`.
- **[?] Проверить в SYNC-2:** точный синтаксис `tailscale serve` для установленной версии и работу VPN-по-требованию на iPhone.
- **Статус:** Принято (2026-10-20).

## D-12. Процесс Telegram-бота
- **Варианты:** фоновая задача внутри процесса FastAPI; отдельная команда с той же БД.
- **Рекомендация:** отдельная команда `python -m app.telegram` — проще отлаживать и перезапускать; общий код — `ReportService`.
- **Статус:** Предложено.

## D-13. Платформы таргета
- **Контекст:** основной таргет объявляет macOS и visionOS (`SUPPORTED_PLATFORMS`), но код использует `UIKit` без условий в `AppDelegate.swift`; сборка под эти платформы не проверялась.
- **Решение владельца:** пока только iOS. Поддержка macOS/visionOS не проектируется и не проверяется.
- **Следствие:** в roadmap добавлена необязательная задача PLAT-1 (убрать macOS/visionOS из `SUPPORTED_PLATFORMS` основного таргета и тестов); выполняется только по отдельной команде, т. к. меняет настройки проекта.
- **Статус:** Принято (2026-10-20).

## D-15. «Цели» и «фокус»
- **Контекст:** в брифе упомянуты цели и фокус, в коде таких сущностей нет.
- **Решение владельца:** цели и фокус — это тексты в файлах Obsidian, а не отдельные сущности приложения.
- **Следствие:** новых моделей, полей и синхронизации для целей и фокуса не будет. Их покрывает read-only просмотр Markdown (фаза 4). Если позже понадобятся, LLM-сценарии могут брать текст выбранной заметки как контекст, но только явно выбранной пользователем и с подтверждением перед отправкой.
- **Статус:** Принято (2026-10-20).

## D-16. Формат файла бэкапа
- **Контекст:** BASE-2 — ручной экспорт; позже SD-5 — восстановление из этого же файла.
- **Варианты:** (а) два файла `mytasks.json` + `profile.json` как есть; (б) один JSON-файл с заголовком и вложенными `MyTasksDocument` и `ProfileDocument`.
- **Решение:** (б), `BackupDocument` в `Persistence/BackupExport.swift`: `format = "braineeapp.backup"`, `version = 1`, `exportedAt`, `tasks`, `profile`. Один файл проще сохранить и восстановить; вложенные документы — те же типы, поэтому правила обратной совместимости JSON действуют и для бэкапов. Заголовок позволяет отличить бэкап от случайного JSON и отклонить файл более новой версии.
- **В бэкап входит:** все задачи (включая корзину), группы, теги, привычки, профиль (имя, возраст, пол, дата создания), тема и акцент. **Не входит:** аватар (решение владельца 2026-10-20 — не утяжелять файл) и прочие настройки UserDefaults (уведомления, вкладки, отображение списка).
- **Следствие для SD-5:** восстановление из бэкапа не должно стирать текущий аватар, если в файле его нет.
- **Статус:** Принято (2026-10-20).

## D-17. Схема SwiftData: версионирование и ограничения
- **Контекст:** SD-1 — `VersionedSchema` и фабрика контейнера (`Persistence/Schema/SchemaV1.swift`, `Persistence/ModelContainerFactory.swift`).
- **Варианты:** (а) `SchemaV1.models` ссылается на текущие классы из `Models/`; (б) сразу перенести классы внутрь `SchemaV1` + `typealias`.
- **Решение:** (а). Маленький diff, остальной код не трогается. **При появлении SchemaV2** классы V1 нужно скопировать в `extension SchemaV1` в нынешнем виде («заморозить»), иначе миграция невозможна; имена сущностей = имена классов (проверяет тест).
- **`#Unique` на `uuid` (решение владельца 2026-10-20):** добавлен во все 5 моделей прямо в V1 — постоянное хранилище ещё нигде не создавалось, поэтому отдельная версия схемы не нужна. Следствие: вставка записи с существующим `uuid` обновляет её (upsert), а не создаёт дубль — и в памяти, и в файле. Мигратор SD-2 опирается на это поведение.
- **`@Attribute(.externalStorage)` для аватара — не добавляем (решение владельца 2026-10-20):** аватар — локальная кастомизация; его потеря при удалении и переустановке приложения некритична, владелец ставит его вручную.
- **Статус:** Принято (2026-10-20).

## D-18. Мигратор JSON → SwiftData
- **Контекст:** SD-2 — `Persistence/JSONToSwiftDataMigrator.swift`, пока не подключён к старту.
- **Источник:** только чтение. `AppDataStore.readTasksSource` / `readProfileSource` выбирают файл или Keychain по тем же правилам, что `loadTasks`, но без нормализации (чтобы отчёт видел, что она отбрасывает) и без записи на диск. Битый файл без Keychain-копии — ошибка, ничего не меняется.
- **Бэкап:** `Application Support/Backups/pre-swiftdata-<yyyyMMdd-HHmmss>/` — `mytasks.json`, `profile.json` и Keychain-копии (`keychain-*.json`), каждая копия сверяется побайтно. Ошибка бэкапа — перенос не начинается.
- **Копирование:** upsert по `uuid` (`#Unique`, D-17) через `AppDataPersistence.importTasks/importProfile` — одно место маппинга JSON → модели. Пока маркера нет, хранилище не источник правды: записи, которых нет в JSON (остатки прерванной попытки), удаляются. Профиль без `id` при повторе берёт `uuid` из прерванной попытки.
- **Проверка:** новый контекст, каждая запись по `uuid` сравнивается со всеми полями JSON; лишние и недостающие записи — ошибка.
- **Маркер:** `Application Support/BraineeApp/swiftdata-migration.json` (версия схемы + отчёт), пишется только после проверки. Есть маркер — повторный запуск ничего не делает.
- **Отчёт:** количества до/после, дубликаты по сущностям, привычки сверх 7 и с пустым названием, убранные висячие ссылки на группы и теги, удалённые устаревшие записи.
- **Статус:** Принято (2026-10-20).
